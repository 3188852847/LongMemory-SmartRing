## 结论与样本边界

当前 buffered 选择会等待完整文本段的语音生成，然后才交付可编码音频。
这足以解释为什么“服务已热身”仍不等于新回复能立即出声；不能据此确定本次
3.9～4.1 秒分别花在语音 token 生成、Flow、HiFT、参考音频处理或清理的哪一步。
未发现提示策略在 TTS 路径新增固定三秒等待的代码。

## 两处完整段屏障

1. [客户端请求与交付](../../../scripts/development/xiaozhi/cosyvoice_streaming.py)：
   第 467 行默认 `buffered`；第 503～507 行虽发送 `stream:true`，同时明确发送
   `delivery_mode:buffered`。服务端 v2 处理器据 delivery_mode 显式传
   `model_streaming=False`，不采用服务的全局默认值。
2. [服务端 stream_chunks](../../../scripts/development/cosyvoice/service.py)：
   第 381～443 行在 buffered 下收集全部内部输出，耗尽模型生成器之后才发布。
   固定 CosyVoice 源码 `074ca6dc9e80a2f424f1f74b48bdd7d3fea531cc` 的
   `cosyvoice/cli/model.py` 中，CosyVoice3 继承的 `tts(stream=False)` 先
   `join` 语音 token 生成线程，再对完整 token 做 Flow/HiFT 波形合成。
   耗尽生成器还包含既有 CUDA 清理/同步；本次没有其独立耗时证据。
3. 客户端第 558～564 行继续累积 PCM，读到段末才一次送入 Opus 编码器。
   因而收到 HTTP 响应头或首个传输块不等于首帧可发送。

服务端与客户端屏障处于同一条流水线，不表示两次各多等四秒。
`X-LongMemory-Audio-Stream:2` 证明传输协议，不单独证明模型增量或缓存命中。
目前观测的“首 Opus 帧”也可能含前导静音，不等于首个有效字音或设备实际播放。

## 已有候选是否能直接选择

入口为 [启动接线](../../../scripts/development/xiaozhi/launch_with_memory.py) 第 453 行
`--cosy-delivery-mode`，非 buffered 还要求相应流水线启用。下表说明代码能力，
不表示本轮已修改日用启动参数或完成当前声线的实机验收。

| 模式/能力 | 当前代码行为 | 本轮状态及缺口 |
|---|---|---|
| buffered | 请求非增量模型；完整段 PCM 才编码 | 主会话报告日用仍选择它；本轮分析基线 |
| incremental | v2 请求显式开启模型增量；收到 PCM 即编码 | 已有选择器，不需另加服务 `--model-streaming`；须确认运行实例 finally 适配已应用、未强制 buffered，补当前声线真实首声、供给间隙和取消复用证据 |
| adaptive | 同样请求模型增量；独立读流与自适应播放缓冲 | 已有选择器；初始目标 360ms、容量 3000ms，欠载恢复可提高目标；3000ms 是容量，不是每段固定等待。须补当前基线真实验证 |
| 隐藏层优化/取消适配 | 服务默认启用 hidden-only；固定源码适配负责 finally 清理与取消 | 已有能力，实际是否应用以运行实例诊断为准，不能只看参数默认 |
| TensorRT/vLLM | 固定上游支持相应加载选项；当前服务只构造 `CosyVoice3(..., fp16=True)` | 当前接线未加载；不属于本次直接切换候选，不做导出、安装或接入 |

`incremental` 的首块仍要等足够语音 token、前瞻上下文及首次波形计算；不会因为名称而立即出声。
服务 `force_buffered_audio` 会覆盖增量请求，必须检查实际能力状态，不能仅凭 v2 响应头判断。
正常 HTTP 生成门采用非阻塞获取，忙时 503；没有发现这里主动排队四秒的策略。
模型还有串行锁，但目前没有本次锁竞争证据。

旧同文本、同种子窗口见 [先前合成记录](AD-cosy-continuity-20261021.md) 的真实 GPU 阶段：
adaptive 在当时两组公开合成文本中较 buffered 早约 0.2～0.35 秒取得首帧，
但完整生成更慢；它没有达到首帧一秒内。该窗口使用旧代码和默认声线，不能换算为
当前两条 3.9～4.1 秒样本的收益，也不能作为当前设备体验通过的证明。

## 热身、分段与尚未测量的部分

- [服务构造与热身](../../../scripts/development/cosyvoice/service.py) 第 162、218～240 行：
  模型常驻，不按每段重载；默认参考做一次完整热身，存在已选档案时另做已选声线热身，
  适配成功时后者走增量路径。ready、热身完成、选中身份匹配是不同事实。
  主会话报告 PID 3172 热身正常，本会话未另查健康接口；即使全部正常，仍须为新文本做语音生成。
- 完全相同的近期文本可命中进程内回复缓存；不同文本、声线或交付模式不会因此免合成。
  当前具名说话人缓存可复用提示特征，不代表新的文本语音 token 已缓存。
- [自然分段](../../../scripts/development/xiaozhi/cosyvoice_segments.py) 第 26～102 行：
  首个自然边界达到 8 字可发送；过短开头合并至满足 16 字的自然边界，后续默认 18 字，
  最后不足阈值尾段在结束时清空。服务前端仍可能再做文本规范化/拆段。
  本次脱敏 TTS 记录没有首段字数，不能从 3.9 秒反推长度。
  后两条等待已落在首段 TTS 内，单改此前的分段等待不能据此保证消除这几秒。
- 选中参考 WAV 的读取/校验、模型 token 生成、Flow、HiFT、PCM 转换及结束清理都有成本；
  目前没有本次各阶段差值。默认热身与长期稳定态不能仅由两条样本区分。
  不据此删校验/清理、缩短模型 hop，或每次回复额外热身。
- [已有运行诊断](../../../scripts/development/cosyvoice/runtime_diagnostics.py) 提供
  `llm_job`、`flow.inference`、`hift.inference`、`frontend.text_normalize` 累积次数/墙钟耗时。
  可在获准的新窗口取前后差值；这些阶段可能重叠，且没有额外 CUDA 同步，不能相加当纯 GPU 时间。

通过本轮“可比较诊断”的门槛：

1. 实际模式/适配/强制缓冲状态可核对，选中声线身份不变；无 busy、回退或实例重启。

   有能量代理可统一用连续至少 5ms、16 位 PCM 绝对幅度至少 200，不宣称这是听见首字。
3. 完整案例结束/采样数/尾帧可核对，无重复交付或可检测截断；取消后线程与模型请求状态归零，下一次可正常合成。
