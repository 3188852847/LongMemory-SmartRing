# ADR-0062：主动交流单次执行编排器

- 状态：已接受；Fake 投递闭环完成，真实小智适配与后台调度未接入。
- 日期：2026-09-06。
- 承接：ADR-0058、ADR-0059、ADR-0060、ADR-0061。

## 背景

P4 已分别具备受限主动播报探针、持久事件账本、确定性许可策略和用户设置，但这些部件尚未形成一条可验证的执行链。如果直接加入定时器或圆屏调用，策略、并发幂等和外部副作用会同时变化，失败后难以判断是哪个环节造成的。

小智现有主动播报接口只返回服务端 `queued`，没有设备播放完成回执。编排器不能把该结果升级成已传输、设备已确认或已播放。

## 决定

1. 新增单次 `ProactiveOutreachDispatcher`，输入只能是已经写入账本的候选、预期 revision、当前主体的持久设置和由运行时汇总的可信状态。
2. 编排器先运行纯许可策略。`WAIT` 不修改账本；过期写入 `expired`；其他阻止原因写入 `blocked`，且都不调用投递端口。
3. 策略允许后，必须先以 revision 条件把候选推进到内部 `queued`，再调用外部投递端口。这样多个执行者竞争时只有一个能产生外部副作用。
4. 第一版投递端口只表达“接受排队”或“拒绝排队”。接受后账本仍停在 `queued`；没有更强证据时不得生成 `transport_sent`、`device_acknowledged` 或 `played`。
5. 投递拒绝或异常从 `queued` 进入 `failed`。异常正文不写入数据库，只保存稳定原因 `delivery_exception`，避免第三方错误意外携带密钥或对话内容。
6. 本切片不创建候选、不生成文本、不扫描数据库、不启动定时器、不自动重试，也不接触真实小智或圆屏。实际投递适配器和运行时状态汇总分别作为后续小切片接入。

## 理由与后果

先把单次执行做成独立应用用例，可以使用 Fake 投递器验证状态机、许可和幂等，同时保持设备供应商可替换。先占有账本再调用外部系统减少重复播报风险，但进程若在两者之间崩溃，记录会停在 `queued`；恢复流程必须把这种结果视为未知或失败，不能重放过期内容。

## 失败预演与回退

- 两个执行者同时处理同一 revision：后者在外部调用前得到冲突，不重复投递。
- 设置关闭、勿扰或候选未到时间：投递端口不会被调用。
- 小智拒绝或抛出异常：事件记录失败，不自动重试；异常详情仅进入受控运行日志时也应脱敏。
- 进程在写入 `queued` 后退出：后续恢复器不得假设消息已播放，也不得直接补播。
- 回退时删除编排器接线即可；V14/V15 数据结构、已有事件和设置无需回滚。

## 验证

- 集成测试覆盖允许后只停在 `queued`、revision 防重复、投递拒绝、异常脱敏、未到时间、总开关关闭及持久勿扰。
- 测试使用临时 SQLite 和 Fake 投递，不调用模型、个人数据库、小智服务或真实圆屏。
