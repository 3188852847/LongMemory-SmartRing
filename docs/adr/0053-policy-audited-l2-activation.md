# ADR-0053：L2 自动生效必须使用独立策略身份和受控执行器

- 状态：已接受
- 日期：2026-09-06
- 关联阶段：P3.9

## 背景

P3.9 要把 L1 低频整理成 L2。原有 L2 复核表只允许 `user`，如果后台直接复用它自动接受候选，数据库会把系统判断伪装成用户判断。另一方面，模型预览虽然限制来源白名单和最少两条 L0，却不能自行决定候选应否进入回答路径。

## 决定

1. SQLite V12 将 L2 复核身份扩展为 `user / policy`；旧记录原样保留为 `user`。
2. `policy` 只能接受，不能自动拒绝，并必须记录策略版本和稳定决定原因。
3. 首版 `scenario-activation-v1` 要求模型最终选择至少 3 条 L1、覆盖至少 3 条用户 L0，且模型之外的风险输入没有敏感内容、来源角色歧义或未解决冲突。2/2 仍可成为人工候选，但自动路径保持 HOLD。
4. 三条来源门槛是保守产品护栏，不是语义蕴含证明或研究结论。模型摘要仍可能不忠实，后续应增加语义支持检查和真实使用复核。
5. L1→L2 执行器一次至多调用候选模型一次，不重试。模型 `candidate=null` 记为正常完成并推进游标；网络/格式失败记为失败且不推进；HOLD/BLOCK 不创建候选，但本批证据以后仍可作为旧上下文与新证据再次成组。
6. 候选创建、策略接受和账本完成在同一 SQLite 提交边界内；失败不能留下 active L2 却把账本写成成功。
7. 当前执行器仍是显式的一次性用例，不挂入每轮聊天或后台定时器。

## 后果

- L2 召回不再一律宣称“已经用户复核”，而是如实标记“已经复核或策略门控”；详情 API 暴露实际身份、版本和原因。
- 个人库已在一致性备份后完成 V11→V12 前向迁移；既有 L2 及人工复核计数不变，迁移本身没有创建、接受或改写 L2。
- 下一步可以在不改变候选/复核事务的前提下接入低频触发，再建设 L2→L3 整理。
