# ADR-0058：圆屏主动播报通道技术验证

- 状态：已接受；代码侧验证完成，真实圆屏试听待验收。
- 日期：2026-09-06。
- 承接：ADR-0007、ADR-0015、ADR-0047。

## 背景

P4 的第一项未知不是定时器，而是服务端能否在用户没有先说话时，经由已认证的小智连接让 SmartRing-Plus 圆屏终端播放一句话。既有设备控制桥只验证了 MCP 音量工具，不能据此声称待机主动播报可用。

对固定小智快照的源码检查表明：每个活动连接拥有独立 TTS 实例、文本队列和音频队列；普通回答通过 `FIRST → TEXT → LAST` 进入该队列，再由连接事件循环向设备发送 TTS 状态、字幕和 Opus 音频。当前协议没有可供服务端确认“圆屏已经播放完成”的独立回执。

## 决定

1. 在既有 `--device-control` 窄桥中增加技术验证用 `announce` 操作，复用同一个已认证单设备连接和既有 TTS 管线；不改固件、不调用 LLM、不写短期会话或长期记忆。
2. 命令只接受 1–80 字符单行文本和 5–300 秒有效期。请求到达时已过期、设备离线、TTS 未就绪或设备正在讲话/收音/通话/处理队列时立即拒绝，不等待、不打断、不自动重试。
3. 成功结果固定为 `state=queued` 与 `playback_acknowledgement=unavailable`。这只证明服务端已接受并入队，不表示 WebSocket 已送达、设备已显示或扬声器已播放。
4. 继续使用回环地址、文件令牌、固定 Host、无 Origin、无代理、无重定向和 1 KiB 请求上限。不开 CORS，不把令牌交给浏览器，也不开放任意小智方法或设备工具名。
5. 新依赖的上游 TTS 生命周期文件加入快照哈希。文件变化后控制桥拒绝启动，必须重新审查，不能把补丁盲套到未知版本。
6. P4.1 只提供 CLI 实机验证入口。实机通过后再设计持久事件、规则、控制台页面和调度器，避免围绕不存在的投递能力建产品结构。

## 理由与后果

复用小智现有 TTS 管线能让主动消息继续使用当前选中的音色、采样率、字幕和流控，避免维护第二套音频协议。缺点是连接必须保持在线，且当前只能观察“排队”；第一版结果账本必须把 `queued`、传输、设备确认和播放明确区分，不能补造后两种状态。

该技术验证不会在设备离线时保存待播文本，因此没有过期后补播的风险。以后即使引入持久调度，过期问候也必须终止，而不是设备重连后突然朗读。

## 失败预演与回退

- 若圆屏待机态不响应 TTS 状态或音频，CLI 仍可能返回 `queued`；以实机未听到为失败，不扩大结论。
- 若用户恰好开始说话，前置状态检查仍存在毫秒级竞态；验证文本必须无敏感信息，正式 P4 需进一步定义冲突和取消行为。
- 若 TTS 生成失败，当前上游线程只记录错误，桥不会获得完成失败回执；正式事件模型需诚实停在 `queued/outcome_unknown`。
- 回退方式是停止小智并去掉 `--device-control`，或删除本次受限路由；数据库、角色、记忆和固件均不受影响。

## 验证

- 43 项设备控制单元测试覆盖入队、状态能力、输入/有效期、忙碌拒绝、TTS 生命周期顺序和既有音量行为。
- 独立传输探针覆盖 CLI → 回环令牌 HTTP → 控制对象，并继续使用真实上游 MCP 回执路由核对音量路径；主动文本仅进入合成 TTS 发送器，不连接真实设备。
- 真实 SmartRing-Plus 圆屏终端待机试听尚未执行，因此本 ADR 不宣称主动播报已经实机通过。
