# ADR-0094：不保留正文的 L1 删除审计

- 状态：已接受
- 日期：2026-09-09

## 背景

每日记忆回顾已经可以从现有 L1、证据类型和双时间字段区分普通新增、错误纠正与事实变化。但删除会移除 `atomic_memories` 行，旧结构没有独立 L1 删除事件，因此系统既不能可靠显示当天删除次数，也不能证明某次删除确实发生。

把被删正文复制到审计表虽然便于展示，却会违背用户对“删除”的直觉，并扩大个人信息留存面。仅在网页删除入口写日志也不完整，因为 CLI 和圆屏自然记忆操作最终会走其他调用路径。

## 决定

SQLite V28 新增 `l1_deletion_events` 与 `BEFORE DELETE` 触发器：

1. 每次真实删除 `atomic_memories` 行时记录随机事件 ID、原 L1 ID、主体 ID 和 UTC 删除时间。
2. 事件不保存记忆正文、L0 原话、来源 ID、删除原因或操作者身份；无法证明的字段不猜测。
3. 触发器位于数据库边界，使网页、CLI、圆屏或未来适配器只要执行同一 L1 删除，都得到一致审计。
4. V27→V28 只创建空表、索引和触发器，不根据缺失行回填历史删除。
5. 每日回顾可显示删除计数、L1 ID 和时间，并明确正文未保留。

## 后果与边界

- 用户能看到未来发生的 L1 删除，而不会因为审计功能留下被删事实副本。
- 事件 ID 和原 L1 ID 仍属于操作元数据；“删除 L1”仍不等于彻底擦除 L0、聊天旁库、备份或外部模型服务中的数据。
- 当前无法区分删除来自网页、CLI 还是圆屏，也无法显示被删内容；若未来确需原因或可信操作者，必须设计显式操作上下文，不能靠触发器猜测。
- 迁移不会生成个人记忆、删除现有数据或追溯补造历史事件。
