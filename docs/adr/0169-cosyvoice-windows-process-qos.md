# ADR-0169：CosyVoice 在 Windows 显式使用 HighQoS

- 日期：2026-09-15
- 状态：439 项开发测试及实际服务验证通过；当前日用进程已应用，圆屏体验待验收。
- 补充 ADR-0166、0167、0168，不替代声线、切段和播放边界。

## 问题与证据

用户复测后仍不满意。最新 V6 中，首段生成 3879ms、播放 2160ms，第二段生成
6644ms；按完整入队估算，第一段后仍有 4484ms 空档。回答模型首字另需 2443ms。
既有分段优化的独立样本不能代表实际日用进程的速度。

保留日用慢进程，在同一张 GPU 上同时启动同配置独立服务，交替固定公开句且关闭缓存，
旧进程约 2.9～3.7 秒，新进程约 1.3 秒。模型、主要 DLL、性能环境白名单和显式
线程优先级相同；不能据此建议换模型或把多模型常驻直接归为根因。

随后仅对同一日用进程切换 Windows 进程 QoS（性能与节能调度偏好），不重启模型。
两轮“系统默认 → HighQoS → 系统默认 → HighQoS”的短句/数字句对照中，恢复默认
即恢复慢态，HighQoS 则稳定快于实时。数字句默认生成 5.75～5.81 秒，HighQoS
生成 2.23～2.44 秒；音频时长随机变化，按实际时长计算的 RTF 也从约 1.27 降到
0.56～0.59。见[完整实测及局限](../research/cosyvoice-windows-qos-2026-09-15.md)。

微软文档明确：没有显式指定时，Windows 会自行推断 QoS；HighQoS 可由进程明确
请求，区别于提高 CPU 调度优先级。实验支持将进程 QoS 作为可复现的修复控制点，
但尚未把 CPU 选核、频率和 GPU 驱动等待各自的贡献拆开，不声称已经证明 GPU
被某个固定频率锁住。[API 说明](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation)、
[调度层级说明](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service)。

## 决定、范围和完成条件

1. 仅在 CosyVoice 服务命令行入口、加载模型和创建推理线程前，为当前进程请求
   HighQoS。独立模块只接受当前进程，不提供任意 PID、HTTP 修改或全局控制入口。
2. 读取并保留其他控制位，仅接管 execution-speed 位并关闭其节流状态，再读回核对。
   非 Windows、API 不可用或设置失败时保留原运行路径并暴露固定原因码；核对失败
   尝试恢复旧设置。只作用于本次进程生命周期，不写注册表或系统电源计划。
3. `--system-qos` 跳过显式设置，供新进程对照和回退。`/health` 的
   `runtime.windows_qos` 返回启动时是否应用、原因码和前后控制位，不含用户数据。
   这是启动快照，不冒充外部修改后的实时监测。
4. 不改变模型、采样、FP16、参考声线、Flow 步数、Opus、设备固件或 Memory Core；
   不新增依赖。可能提高合成期间功耗，应以实际延迟收益换取这部分开销。
5. 完成条件为安全回退测试、入口顺序测试、实际服务健康回读和同进程可逆性能对照。
   整轮停嘴到首包、圆屏连续性、自然度及打断仍要在真实设备验收，不以固定句替代。

## 失败预演与后续

如果其他电脑或 Windows 版本没有收益，使用 `--system-qos` 进行同条件回退；不得
自动升级为高优先级、锁频或全局高性能电源计划。如果仍有长空档，先核对实际加载
状态及 V6，而不是继续增加首播缓冲。回答模型首字约 2.4 秒仍独立存在，本决定没有
加速它，也没有授予校园接口或个人数据库访问权限。
