# ADR-0036：在实现 L2 前渐进校准记忆内部边界

- 状态：已接受并完成第一切片
- 日期：2026-09-06

## 背景

项目最初围绕 L0/L1 最小闭环搭建，随后增加了共享运行时、模型提取、混合检索、人工纠正和事实变化。设备、模型、TTS 和研究方法已有适配边界，但记忆内部仍有两个结构性问题：L1 的规范模型实际放在通用 `core.memory.models`，而预留的 `l1_atomic/` 为空；应用层 `MemoryRuntime` 会在未注入方法时直接创建 `LongMemoryV1`。如果带着这两个问题继续增加 L2，层级类型和装配职责会进一步混在一起。

全面重写并不合理。当前双入口和个人 V4 数据库已经通过体验，集中改名、移动所有模块或重建存储会带来与用户价值不相称的回归和迁移风险。

## 决定

1. 将 L1 模型和 `MemoryStore` 契约的规范定义放入 `core/memory/l1_atomic/`；项目生产代码使用新路径。
2. 原 `core.memory.models` 和 `core.memory.contracts.MemoryStore` 保留兼容转发，且必须指向同一类型对象，不复制定义。
3. `MemoryRuntime` 只依赖中立 `MemoryMethod` 契约，构造时必须显式注入方法；日常默认的 `LongMemoryV1` 由 `bootstrap.build_memory_runtime` 装配。
4. 增加 AST 依赖回归测试，禁止应用层重新导入具体记忆方法，并禁止生产代码重新依赖旧 L1 模型路径。
5. 本切片不改变 V4 schema、个人数据库、记忆算法、API 响应或控制台行为。

第二切片把“当前完整结构”“迁移调度”和 V1→V2、V2→V3、V3→V4 各代 SQL 分开保存，并用连续迁移注册表调度。拆分没有新增数据库版本，也没有打开或写入个人库。

## 后果

- L2 可以建立自己的模型和契约，不再继续挤入 L1 通用文件。
- 网页、圆屏及实验方法仍通过同一个中立运行时协议，替换策略不要求修改应用编排。
- 旧导入路径暂时存在，降低一次性迁移风险；待外部脚本迁移完成后可另建 ADR 决定是否删除。
- `bootstrap.py` 仍包含既有 L1 兼容应用装配，这是后续可拆分的热点，但不是本切片必须解决的问题。
- 新 schema 版本必须新增单独的来源版本迁移模块；连续性测试会阻止只提高版本号却漏写迁移。
