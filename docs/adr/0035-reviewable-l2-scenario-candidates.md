# ADR-0035：L2 先形成可复核的场景候选，不直接生成用户画像

- 状态：已接受，V5 结构已实现
- 日期：2026-09-06

## 背景

L0/L1 已能保存原话与原子事实，但陪伴助手还需要理解一段时间内正在发生的生活背景，例如“本周正在准备答辩”。直接把若干事实交给模型生成自由摘要会带来三个问题：摘要可能混入无证据推断；来源 L1 变化后摘要仍继续生效；短期偶然事件可能被误写成稳定用户画像。

L2 和 L3 因而必须分开：L2 表达有边界的场景、主题或人生阶段，L3 才表达跨时间重复出现的稳定偏好与行为模式。“用户这周下午一点来聊天”可以是 L2 观察背景，“用户通常下午一点聊天”则是尚待更多证据的 L3 习惯候选。

## 决定

1. 第一版 L2 称为“场景候选”，结构至少包含：稳定 ID、主体、标题、可独立理解的摘要、系统生成时间、可空的现实开始/结束时间、生命周期状态、生成器身份与版本。
2. L2 必须通过独立关联追溯到支持它的 L1；每条 L1 仍可继续追溯到 L0。第一版候选至少需要两条不同 L1，并覆盖至少两个不同的用户 L0 消息，防止把一次话语拆成多个 L1 后伪装成多证据。
3. 自动生成的 L2 初始状态只能是 `candidate`，不进入日常回答上下文。用户查看摘要和来源后可接受或拒绝；只有 `active` L2 才具备以后参与召回的资格。
4. “模型生成”和“用户确认”分别记录，不能把确认后的场景伪装成用户逐字陈述。第一版不使用未经校准的数字置信度。
5. 形成候选时只使用同一主体、当时仍有效的 L1。来源 L1 退役、被纠正、发生事实变化或删除后，相关 L2 必须可定位并标为 `stale`，在重建或重新确认前不得参与召回。
6. 不建立固定场景分类树；标题与时间范围用于组织，避免在没有真实使用证据时提前锁定“工作/情绪/关系”等分类。
7. 第一版由用户在控制台显式触发低频整理，不在每轮聊天后调用模型。自动触发、后台调度和主动问候留到场景质量经过体验后再设计。
8. L2 不覆盖、合并或修改来源 L1，不自动产生 L3 用户画像，也不接收外部文档作为个人证据。

## 首个实现切片

1. 先完成 V5 schema 与 V4→V5 显式备份迁移工具，但不自动迁移个人库。
2. 增加场景候选、L1 来源关联和人工复核存储；先用确定性合成候选验证生命周期，不调用校园模型。
3. 控制台新增 L2 候选列表、来源核对、接受与拒绝；不接入回答上下文。
4. 再增加模型候选生成适配层和显式“整理场景”操作，模型失败时不留下半条候选。
5. 真实体验证明候选有用且来源可靠后，另行决定 L2 检索与上下文注入方式。

## 后果

- 错误 L2 在影响日常回答前有人工复核屏障，且来源变化能使其显式失效。
- 第一版不会立刻带来“助手更懂我”的回答效果；它先建立可靠的派生和管理链路。
- 人工复核增加操作成本。后续只有真实候选数据足以校准自动接受策略时，才考虑减少确认。
- V5 会增加表和迁移成本，因此本 ADR 只冻结语义与验收边界；迁移必须单独实现、测试并获得个人库操作授权。

## 实现记录

2026-09-06 已实现 V4→V5 空结构迁移：新增场景、来源快照、生成审计和人工复核表。现有 L1 允许硬删除，因此 L2 来源保存 L1 ID 与内容快照而不使用指向 L1 的删除级联外键；触发器会在 L1 退役或删除前把相关 candidate/active 场景标记为 stale。该实现不生成候选，也不让 L2 参与回答。
