# ADR-0042：L3 先采用人工候选与可审计生命周期

- 日期：2026-09-06
- 状态：已接受并完成；个人数据库已备份迁移至 V8

## 背景

ADR-0039 只建立了 L3 领域模型和 V7 空表。要让用户开始积累真实画像纠错经验，需要补齐管理闭环；但当前没有经过验证的自动画像生成策略，把模型草稿直接开放会混淆“系统推断”和“用户自述”。同时，L3 若引用随后被纠正、删除或失效的 L1/L2，就不能继续保持生效。

## 决定

1. 第一版由用户在控制台选择有效 L1 或已接受 L2，填写一个原子画像断言并创建候选；不调用模型、不扫描历史、不自动落库。
2. `user_declared` 与 `system_inferred` 使用 ADR-0039 的不同证据门槛。观察日按底层用户 L0 的 UTC 日期计数；这是当前可复现口径，不代表用户所在时区的自然日。
3. 候选、来源内容快照和生成审计原子保存。用户须核对 L0 原话后显式接受或拒绝，复核使用 revision 做并发保护。
4. 新增独立 `--allow-persona-management` 写能力；读取保持可用，创建和复核还必须通过本机会话、同源/CSRF 和请求体确认字段。日常本机启动器显式开放该能力，但服务端和命令行参数默认关闭。
5. SQLite 升级为 V8。L1 退役/删除或 L2 转为 stale 时，关联 `candidate/active` L3 转为 stale，并写入 `persona_lifecycle_events`。来源快照、审计和 L0 证据保留。
6. 已接受 L3 当前仍不进入回答上下文。模型辅助草稿、自动整理和受控召回分别作为后续切片，不因本管理页存在而视为已授权。

## 后果

收益是用户能看见系统为何形成画像，且上游证据变化不会让旧画像继续生效；人工候选也为后续模型草稿提供了稳定 API 和验收基线。代价是第一版录入较慢，UTC 观察日不是最终产品时区语义，失效后还需用户手工重建。

V7→V8 只增加生命周期事件表和失效触发器，不扫描历史、不生成画像、不改写既有 L0/L1/L2/L3。个人数据库必须在服务停止、创建一致性备份并再次明确授权后迁移。
