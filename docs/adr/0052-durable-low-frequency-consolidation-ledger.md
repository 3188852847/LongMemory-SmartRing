# ADR-0052：低频记忆整理使用持久运行账本与确定性触发护栏

- 状态：已接受；账本、两阶段执行器、只读状态与中断收束原语已实现，后台调度待接入
- 日期：2026-09-06
- 关联阶段：P3.9

## 背景

L2 候选生成、L3 `ADD / UPDATE / NOOP`、证据门控和自动生效执行器已经存在，但它们都只处理显式传入的一组来源。若直接在每轮对话后扫描数据库并调用模型，会出现重复整理、并发运行、失败风暴、重启后丢失进度以及无法解释调用成本等问题。

现有“待整理 L1”收件箱只回答一条 L1 是否已被当前有效 L2 使用，不是持久调度器，也不能承担模型预算和运行审计。

## 决定

1. L1→L2 与 L2→L3 共用一个技术中立的整理运行契约，但分别使用独立阶段状态。
2. SQLite V11 新增 `memory_consolidation_runs`。每次运行记录主体、阶段、触发类型、状态、开始/结束时间、来源数量、模型调用次数、稳定结果码和成功高水位；不复制个人记忆正文。
3. 每个主体、每个阶段同一时刻最多一个 `running` 记录。并发抢占失败返回稳定原因码，不同时执行两次模型调用。
4. 只有 `completed` 可以推进由“时间 + 来源 ID”组成的稳定游标。`failed` 和 `skipped` 留痕但不能假装已处理证据。
5. 第一版触发策略默认至少 4 条新来源、6 小时冷却、每阶段每天最多 2 次模型调用、一次最多 20 条来源。它们是可配置的产品运行护栏，不是记忆质量结论或论文超参数。
6. 人工触发可以绕过来源数量和冷却，但不能绕过并发互斥、空输入和每日调用预算。
7. 模型仍只产生候选；既有 L2/L3 证据校验、复核、自动激活和取代事务不被账本绕过。
8. L1→L2 选择按成功游标之后的最老新来源向前推进，不能直接拿最新一批后跨过中间证据。批次有余量时，加入最近的游标前“尚未被候选/有效 L2 使用”的来源作为上下文；它们不重复计入新来源阈值，但可与新事实重新尝试成组。

## 当前实现边界

领域模型、纯触发策略、SQLite 账本、稳定选源、两阶段一次性执行器、策略门控和只读控制台状态均已实现。账本还提供显式中断收束原语，把确认过期的 `running` 标记为 `failed/process_interrupted` 且不推进游标；在调度所有权完成前不会自动调用它，避免第二个进程误伤仍在执行的任务。当前仍未接入对话后的后台触发。

## 备选方案

- 只用内存计数：实现简单，但重启后会重复整理，不能审计。
- 使用 APScheduler 或工作流框架：当前只有单机、单用户、两个固定阶段，引入框架会放大部署和故障面；待出现持久定时任务种类增长等真实触发条件再评估。
- 把游标存成单独可变配置：读取快，但会丢失“哪次运行为什么推进”的证据；当前从成功运行记录恢复游标更透明。

## 后果

- 自动整理多了一张业务表和 V11 前向迁移，但不会改写 L0–L3 内容。
- 崩溃遗留的 `running` 记录会安全地阻止新运行；中断收束必须由取得调度所有权的进程显式执行，不能静默删除旧记录。
- 日常控制台已能展示运行原因、成本和失败，不需要解析终端日志；当前卡片是只读的。
