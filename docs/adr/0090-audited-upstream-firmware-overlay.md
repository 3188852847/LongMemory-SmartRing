# ADR-0090：用可审计补丁层维护 SmartRing-Plus 固件改动

状态：接受（2026-09-08）

## 背景

厂家 B V2 源码来自 GitHub ZIP，没有 `.git` 元数据。源码已能用 ESP-IDF v5.5.4 构建并在实机运行，但不能把 `D:\sr-bv2` 这种本机短路径副本当作项目历史。若直接在副本里修改，GitHub 仓库无法说明改了什么、基于什么版本，也难以在厂家更新后判断补丁是否还能安全应用。

首次基线还暴露两个互相关联的问题：板级实现创建 LVGL `SpiLcdDisplay`，板型配置却选择 Emote message style 和 expression assets；资源加载器因此尝试把资源挂到不存在的 `EmoteDisplay`。与此同时，应用镜像为 `4,126,416` 字节，在 `0x3f0000` 应用槽中只剩 `2,352` 字节，不能直接继续叠加完整状态 UI。

## 决定

1. 不把厂家全量源码复制进 LongMemory 主仓库，也不把本机 `D:\sr-bv2` 当作权威源码。
2. 在 `firmware/smartring_plus/` 保存取得日期、板型、工具链、关键源文件哈希和构建产物哈希；这些元数据不等于上游 Git 提交。
3. 后续修改保存为 `firmware/patches/` 下的统一补丁和说明。应用补丁前必须核对目标关键文件哈希；未知或已修改的上游副本应停止，而不是强行套用。
4. 第一项固件实验只验证显示栈与资源策略一致性及镜像体积，不改记忆核心、服务协议、角色素材、分区表或实机数据。
5. 配置实验先在独立副本全新构建并比较 map、assets 和启动路径；构建通过不自动授权烧录。
6. 只有明确记录恢复镜像、写入分区和预期视觉行为后，才进行下一次实机烧录。

## 备选方案

- **把厂家源码完整 vendoring 到主仓库**：最直观，但体积大、许可证与上游同步成本高，也会把生成组件和研究主体混在一起，当前不采用。
- **直接在 `D:\sr-bv2` 开发**：最快，但本机修改不可追溯，重建或换电脑后难以复现，不采用。
- **立即把 ZIP 初始化为新的 Git 仓库**：能看本地差异，但仍不能补回真实上游提交身份；可以作为临时工作手段，不能替代主仓库中的基线清单与补丁。

## 后果

- 固件变化可以独立审查、回退和迁移，不会让 LongMemory Core 依赖厂商目录。
- 每次厂家升级都要重新核对关键哈希，并可能重做补丁；这是避免把旧补丁静默套到新硬件代码上的必要成本。
- 当前最小下一步是形成一份“LVGL 显示 + 匹配资源策略”的配置实验，不是立即设计角色 UI。
