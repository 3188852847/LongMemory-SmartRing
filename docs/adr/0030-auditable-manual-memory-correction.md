# ADR-0030：用追加与取代实现可审计的人工纠正

- 状态：已接受，第一切片已实现
- 日期：2026-09-06

## 背景

日常使用会暴露错误 L1。原地编辑会抹掉“系统原来记错了什么、用户何时纠正、纠正来自哪里”，硬删除后重建也无法表达两条记忆的关系。现有 `retired_at`、`superseded_by_id` 与 `SUPERSEDE` 语义已经为取代预留字段，但 V3 证据类型只接受普通用户陈述。

## 决定

1. 人工纠正不修改旧 L1：新建一条 L1，把旧 L1 标记为已退役并以 `superseded_by_id` 指向新条目。
2. 纠正输入同时保存为新的 L0 用户消息，证据类型为 `user_corrected`；不调用模型润色或补全。
3. L0、新 L1、证据与旧 L1 退役必须位于同一个 SQLite 写事务；任一步失败全部回滚。
4. 写入前核对详情 revision，拒绝对已经变化或退役的条目重复操作，也拒绝相同内容和当前有效的精确重复内容。
5. 第一切片只允许声明“旧记录本来就错误”。“事实后来发生变化”需要 `valid_from/valid_to`，不能冒充人工纠错。
6. schema 升到 V4，仅扩展证据类型约束。控制台不静默迁移已有个人库；提供显式工具，在升级前创建 SQLite 一致性备份并输出 SHA-256。
7. 普通 API 默认不开放纠正；统一日常启动面板会加 `--allow-memory-correction`，网页中每次仍需查看旧内容、输入新事实并明确确认。硬删除保持默认关闭。

## 后果

- 当前召回只读取未退役记忆，因此纠正后旧事实自动退出日常召回，新事实进入召回。
- 历史、原始来源和纠正来源可审计，也能积累后续研究所需的真实纠错信号。
- 旧 V3 日常数据库升级前不能由 V4 控制台打开；用户必须停止服务后显式执行迁移。日常库已于 2026-09-06 经用户授权完成迁移，迁移前 V3 备份保存在被 Git 忽略的 `data/backups/`，完整性与外键校验通过。
- 当前没有撤销纠正、事实变化、自动冲突判断或跨层 L2/L3 传播；这些能力另行设计。
