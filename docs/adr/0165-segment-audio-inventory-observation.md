# ADR-0165：按 TTS 片段观测可播放音频库存

- 状态：已接受
- 日期：2026-09-14

## 背景

CosyVoice3 已把模型内部 WAV 块合并为标点边界内的连续 PCM，并把过短分句合并。真实
数据证明 TTS 请求由 33 段降为 14 段，但现有 V5 时序只记录每段生成耗时，不知道该段
最终可播放多久。因此无法区分“下一段虽然生成慢但被前段音频覆盖”和“设备必然在标点
处断粮”，继续调整字符阈值只能依赖主观听感。

## 决定

圆屏语音时序升级为 V6。每次调用 TTS 时继续记录开始、完成和生成耗时，并在同一调用
期间累计交给 Xiaozhi 队列的 Opus 包数。当前链路每包固定为 60 ms，因而同时暴露
`audio_duration_ms = opus_packets × 60`。

句柄仍绑定当前进程内的话轮 token、句子 ID 和片段序号。上一轮迟到的回调不能写入新
样本。控制桥只接受包数与时长的精确倍数关系，并继续兼容 V1–V5。数据不包含输入、回答、
音频字节、Opus 字节、设备标识或供应商响应。

## 理由

相邻片段音频入队完成时刻之差减去上一段可播放时长，可以近似揭示服务端供给缺口。该
证据能判断播放等待来自片段长度还是模型吞吐，并为隔离加速运行时提供同一验收口径。
只计数已有回调，不改变声音、分段、缓存、发送节奏或设备协议。

## 后果

- 下一轮新对话才会产生 V6 数据；旧 V5 样本无法补算音频时长。
- 估算反映服务端音频库存，不等同于扬声器端真实播放时钟；设备网络抖动仍需另行测量。
- 若未来改变 Opus 帧时长，必须先把帧时长加入协议，不能继续写死 60 ms 换算。
