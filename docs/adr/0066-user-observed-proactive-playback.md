# ADR-0066：以所有者观察补充主动播放证据

- 状态：已接受并实现。
- 日期：2026-09-07。
- 承接：ADR-0058、ADR-0059、ADR-0064、ADR-0065。

## 背景

2026-09-07，用户通过 React 手动问候入口进行真实 SmartRing-Plus 圆屏终端验收：控制台账本显示 `queued`，圆屏实际发出了声音。这证明服务端排队到真实播放的链路在本次环境中可用，但现有小智协议仍没有逐条播放完成回执。若系统自动把所有 `queued` 改成 `played`，离线、断流或播放中断时会制造错误事实。

## 决定

1. 保留 `queued` 的严格含义：只证明小智服务端接受排队。
2. 所有者亲耳听到后，可以在最近运行记录中显式点击“确认已听到”。系统以 `USER_OBSERVED` 证据追加 `user_confirmed_playback` 事件，把 `queued / transport_sent / device_acknowledged` 推进为 `played`。
3. 确认接口要求同源会话、CSRF、精确主动项 ID 和预期 revision；重复确认返回已有 `played`，不重复写事件。
4. 被拦截、失败、过期或取消的项目不能确认播放。确认操作不调用设备、模型或 L0–L3，也不改变问候设置。
5. 允许从 `queued` 直接进入 `played`：用户观察是比当前不可观察传输中间态更强的证据，无需伪造缺失的 `transport_sent` 或设备 ACK。

## 后果与局限

事件账本现在能够保存真实人工验收，而不降低自动证据门槛。它仍依赖所有者诚实点击，不是设备遥测；未来如果固件或协议提供逐条播放回执，应新增 `DEVICE_ACK` 路径并保留两种证据来源的区别。

## 验证

- 真实环境：用户报告圆屏发声，控制台显示 `queued`，符合预期证据边界。
- 领域测试覆盖 `queued → played` 的用户观察跳转。
- HTTP 测试覆盖 CSRF、revision、重复确认及 `USER_OBSERVED` 事件。
- React 测试覆盖只有显式点击才调用一次确认接口。
