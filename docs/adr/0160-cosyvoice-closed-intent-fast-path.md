# ADR-0160：CosyVoice3 封闭寒暄预置语音快速通道

- 状态：已接受
- 日期：2026-09-14

## 背景

真实圆屏最近一轮从进入回答链路到首音频约 6.62 秒，其中记忆准备约 0.08 秒、回答模型首输出约 2.40 秒、首段 CosyVoice3 约 4.10 秒。固定短句在完整日用组合中的首块约 3.23～3.51 秒；同代码独立运行时约 1.48～1.63 秒。缩短首句、额外短句预热和临时提高进程优先级均未消除完整组合的等待。

“你好”“在吗”“谢谢”“晚安”等输入不需要记忆推理或开放式模型创作。继续让它们经过回答模型和实时 TTS 会支付完整延迟，也不会提高答案正确性。

## 决定

为 CosyVoice3 增加严格封闭的本地快速通道：

1. 只对完整输入等于白名单表达时命中；忽略空白和常用标点，但不做包含匹配、模糊匹配或语义分类。
2. 首批只包括普通问候、在线/听觉确认、致谢和晚安。回复分别固定为四条中性文本，不声称已经召回记忆、完成任务或理解未知内容。
3. 用户原话仍调用当前 Memory 查询入口，使 L0、提取审计和后续会话归档保持一致；返回的召回内容不参与这类固定回复。
4. 不调用回答模型。助手文本仍写入当前对话，并由已有回答完成回执归档。
5. 四条回复使用当前固定 CosyVoice3 参考声线预先生成 24 kHz 单声道 WAV。播放复用现有 FIRST/MIDDLE/LAST、Opus 编码、字幕、打断、设备发送和时序观察，不建立第二套播放协议。
6. 只有小智配置精确指向受控的 `127.0.0.1:18770` CosyVoice3 服务时启用；EdgeTTS、VoxCPM2、sanoTTS 和未知自定义 TTS 保持原行为。
7. 普通 CosyVoice3 分块回答启用固定容量的进程内 LRU 音频缓存；只有完整文本完全相同才复用，服务停止即消失，不写磁盘或日志。它用于重复确认语和固定操作回执，不宣称改善首次或独特回答。

## 未采用

- 不把所有问题先播放“我想一下”。固定填充语会增加打断和两段割裂，且只能改善感知等待，不能减少计算时间。
- 不为“我记得”“已经处理”等结论制作预置语音。这些表述必须等待真实记忆或操作结果。
- 不使用关键词包含匹配。例如“你好，帮我看看明天的安排”必须进入正常记忆和模型链路。
- 不在每次启动时重新合成预置音频。这样会延长启动并重新引入本次要绕开的模型成本。

## 后果

- 命中的四类寒暄可以跳过回答模型和实时 TTS，首声主要剩本地 WAV 读取、Opus 编码与设备发送，具体耗时仍以真机记录为准。
- 预置回复会比开放式模型更稳定，也可能更容易重复；因此范围保持小且只覆盖没有信息负担的表达。
- 更换 CosyVoice3 固定参考声线时必须重新生成并听检四个音频文件，不能继续使用旧声线资产。
- 一般问题的 3～4 秒 TTS 首块缺陷仍未解决；后续继续测量常驻进程资源、CUDA 空闲恢复和可替换声音方案。
