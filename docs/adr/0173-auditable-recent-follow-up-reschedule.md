# ADR-0173：最近唯一一次性跟进采用追加式改时

## 背景

V1 已支持从明确的“日期＋时刻＋到时候问我”创建一次性跟进，也支持取消最近唯一一条
未执行跟进。2026-09-16 真实圆屏验收中，所有者在成功安排 21:00 跟进后说“请把时间
改成20点49分”。回答模型声称已经修改，但后台仍只有 21:00 原安排。当前应用层没有
改时命令，模型口头承诺不能代表账本变化。

原地覆盖候选和主动交流投影会丢失旧时间及用户为什么修改的证据；仅禁止模型承诺虽然
能避免误导，却不能满足一次性事项的基本修改需要。

## 决定

1. 增加高精度改时命令，首版只接受类似“请把时间改成20点49分”或带明确时段的
   “请把时间改成晚上九点”。没有时段的 1～12 点继续视为歧义；“晚一点”等模糊表达
   不执行。
2. 目标必须是最近 30 分钟内创建、仍在未来、尚未执行且恰好唯一的一条自然对话跟进。
   零条、多条、已经到点或已开始执行时不得猜测。
3. 新时间沿用原候选的当地日期，只修改时和分；新时间必须晚于当前时刻。首版不通过
   “改时间”隐式改变日期、事项内容或追问短句。
4. 不原地覆盖旧候选。一个事务内先把旧主动账本追加为 `cancelled`，原因码为
   `user_rescheduled_recent_follow_up`，再取消旧候选，并用同一 L1 来源和追问短句创建
   新候选。旧安排已启用时新安排继续建立一次性账本；旧安排未启用时新安排仍只保留
   候选。
5. 修改话语保存为新的用户 L0，但不提取成 L1。成功、时间已过、没有目标、目标不唯一、
   已经执行和时间相同都由应用层固定回执，回答模型不得自行宣称成功。
6. 任一步失败时整个事务回滚，旧安排保持原状；不得出现旧安排已取消而新安排未建立的
   半完成状态。

## 后果

- 圆屏用户可以连续完成“安排 → 改时”，后台、回答和实际投递使用同一账本事实。
- 修改保留旧候选、旧账本和取消原因，能够解释原时间为什么不再触发。
- 用户想修改日期、事项或追问内容时，首版仍需取消后重新创建，避免自然语言指代错误。
- 多条并存时必须进入控制台选择具体目标；系统不按文本相似度猜测。
