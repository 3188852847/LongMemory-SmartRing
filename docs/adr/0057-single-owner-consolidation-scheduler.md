# ADR-0057：由常驻 MemoryRuntime 单一拥有低频整理调度器

- 状态：已接受并实现；真实整理需显式开启，默认关闭，官方模型隔离合成验收通过
- 日期：2026-09-06

## 背景

网页与 SmartRing-Plus 圆屏终端已经共用一个常驻 `MemoryRuntime`。如果网页、圆屏桥或
小智进程分别启动整理定时器，同一批 L1/L2 可能被重复处理；如果直接在聊天请求中整理，
用户还会被候选生成与风险复核的两次模型请求阻塞。此前运行账本也没有单列风险复核器
版本，失败运行难以完整复盘。

## 决定

1. 控制进程中的常驻 `MemoryRuntime` 是低频整理调度器的唯一生命周期所有者；网页和圆屏
   只通过该 Runtime 产生新证据信号，不各自创建调度器。
2. 聊天完成 L1 写入后只发送常数时间、可合并的唤醒信号。候选生成、风险复核和数据库整理
   在唯一守护线程中串行运行，不持有聊天 Runtime 的 SQLite 锁。
3. 每个后台周期必须自行打开并关闭数据库及模型资源，不复用聊天线程的 SQLite 连接。
4. 调度器默认关闭；关闭时不创建线程、不扫描数据库、不调用模型。启动面板高级设置或
   命令行 `--enable-memory-consolidation` 才会显式装配真实两阶段执行器。
5. SQLite V13 为 `memory_consolidation_runs` 增加可空的
   `risk_reviewer_version`。新运行从占用槽位起固定记录该版本，完成和失败都保留；旧记录
   因历史信息不可恢复而保持空值。
6. 进程关闭时 Runtime 先停止调度器，再关闭聊天记忆资源。若外部模型请求尚未返回，等待
   有界；真正装配前仍需保证客户端自身有超时，不能依靠线程强制终止。

## 后果与边界

- 高频聊天不会直接承担低频整理延迟；同一进程只有一个调度所有者。
- `Event` 合并只减少重复唤醒，最终幂等仍由持久运行槽位、游标、冷却和预算保证。
- 守护线程不是可靠作业队列；进程退出后的恢复仍依赖运行账本的中断收束原语。
- 已实现一个周期内先 L1→L2、再按条件 L2→L3，并通过独立 SQLite 连接完成离线及
  官方模型合成闭环；合成测试只产生 1 条 L2，L3 在门槛处停止。尚未为个人库开启。
