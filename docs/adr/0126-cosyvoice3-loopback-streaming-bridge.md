# ADR-0126：CosyVoice3 本机分块语音桥

## 状态

已接受，2026-09-13。部分取代 ADR-0123 的“圆屏只能整段缓冲”决定。

## 背景

真实圆屏首轮样本中，CosyVoice3 首包约 9.11 秒，其中首段完整 WAV 生成与编码约
7.11 秒。服务重启并预热后的第二轮样本降至约 3.81 秒首包，但六段 TTS 仍串行
生成至约 18.90 秒。记忆准备分别只有 12 ms 和 5 ms，主要等待不在 LongMemory。

模型的 `inference_zero_shot(..., stream=True)` 会逐块产生音频，但通用 Xiaozhi
`CustomTTS` 必须等 HTTP 正文完整返回。只修改能力标签不会改变这条数据路径。

## 决定

1. 保留 `POST /v1/audio/speech` 完整 WAV，继续供网页试听、固定测试和兼容回退。
2. 增加只监听 `127.0.0.1:18770` 的 `POST /v1/audio/stream`。响应使用 4 字节大端
   长度加独立 PCM WAV 块，不把私有传输协议暴露到局域网或浏览器。
3. 只在固定 CosyVoice3 URL 下，为当前 Xiaozhi 连接安装运行时分块消费者；不修改
   第三方源码，不影响 EdgeTTS、VoxCPM2 或 sanoTTS。
4. 每个 WAV 块到达后立即复用 Xiaozhi 的 Opus 编码与现有播放队列。首块前失败可
   回退完整 WAV；已经发送音频后不重播整句。
5. 用户打断或服务断开时关闭 HTTP 响应并停止继续交付。模型在下一次产出时才观察
   到断开，因此能力只声明 `cooperative`，不宣称即时 GPU 抢占。
6. 不改变文本切句、回答内容、声线、记忆、圆屏固件和个人数据库。

## 后果

- 预期首声不再等待整个首句音频生成完，后续长段也可以边生成边进入圆屏播放队列。
- 传输块是项目内部协议，不作为公共 API；服务端与 Xiaozhi 启动适配器必须同步升级。
- 模型本身仍串行使用 GPU，回答模型首字等待和音频播放时长不会因此消失。
- 是否改善首声和段间停顿必须用重启后的新圆屏样本验证，单元测试只证明协议边界。

## 回退

移除 CosyVoice 运行时分块安装即可恢复完整 WAV 路径；无需迁移配置、记忆或固件。
也可以在设置或启动面板把下一次 TTS 改回 EdgeTTS。
