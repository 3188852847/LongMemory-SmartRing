# ADR-0048：自动激活使用独立策略复核身份

状态：已接受

日期：2026-09-06

## 背景

L3 原有复核表只允许 `reviewer_type=user`。P3.6 若直接复用这条写入路径，确定性策略作出的自动接受会在审计记录中看起来像用户亲自确认，破坏来源真实性。另一方面，`HOLD / ASK_NATURALLY / BLOCK` 只是处置决定，并不等于一次画像复核，不能为了记录决策而把候选改成已接受或已拒绝。

## 决定

1. SQLite 结构升级到 V10，`persona_reviews.reviewer_type` 区分 `user` 与 `policy`。
2. `policy` 复核只允许 `accepted`，且必须保存非空 `policy_version` 与 `decision_reason`；自动策略不得伪装成用户，也不得通过复核表伪造一次自动拒绝。
3. `user` 复核继续沿用原行为，并禁止携带策略元数据。V9→V10 迁移将既有记录原样保留为用户复核，两个新增字段为空。
4. 画像激活、候选式取代、目标 revision 校验和复核审计继续由同一个存储事务完成。P3.6 只能调用这条既有原子路径，不能另写“快捷激活”。
5. 详情 API 和内部控制台显示复核来源、时间、策略版本与原因，便于之后发现、解释和回退自动决定。
6. 本切片只提供审计能力，不连接自动激活策略，不迁移或写入个人数据库。个人库必须在服务停止、一致性备份和再次明确授权后从 V9 升级到 V10。

## 后果

收益是用户确认和策略决定在领域模型、数据库、API 与页面上均可区分，后续自动化不会污染审计历史。代价是数据库增加一次迁移，并且运行新代码前个人 V9 库必须先备份和迁移。`HOLD / ASK_NATURALLY / BLOCK` 的观察记录仍需在后续候选处置或运行事件设计中解决，不能滥用复核表承载。

## 回退

在尚未产生 `policy` 复核前，可以停止使用新代码并从迁移前一致性备份恢复 V9 数据库。数据库不提供自动降级；一旦产生 V10 策略复核，降级会丢失策略身份和原因，因此必须保留 V10 或执行另行审计迁移。
