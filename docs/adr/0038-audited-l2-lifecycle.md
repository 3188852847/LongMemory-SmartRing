# ADR-0038：L2 失效必须通过可审计生命周期事件

- 状态：已接受并实现；个人库已备份迁移至 V6
- 日期：2026-09-06

## 背景

V5 能在来源 L1 退役或删除时把候选/已接受 L2 标为 `stale`，但只保留最终状态。用户无法区分场景是主动结束、来源被纠正，还是来源被删除，也无法审计发生时间和对应修订。直接在页面原地覆盖状态或有效期会破坏项目的“派生记忆可纠正但必须留痕”原则。

## 决定

1. V6 新增 `scenario_lifecycle_events`，记录场景 ID、动作、操作者类型、发生时间、前后状态和操作后的 revision。
2. 第一版动作只包含用户手动结束、来源 L1 退役、来源 L1 删除；不把重建、恢复或任意编辑提前塞进同一接口。
3. 用户手动结束只允许作用于 revision 匹配的 `active` 场景。在一个事务内将其变为 `stale`、revision 加一、将未知或更晚的 `valid_to` 收窄到操作时间，并追加事件。
4. L1 退役/删除继续由数据库触发器保证跨入口一致性，但触发器先写系统事件再改状态；已经 `stale` 的场景不重复写事件。
5. 失效不物理删除场景、L1 内容快照或 L0 证据。详情页继续展示完整来源和生命周期。
6. V5→V6 迁移只建立空事件表并替换触发器。迁移前的历史原因未知，因此不得回填猜测事件。

## 未选择的方案

- 只增加一个 `stale_reason` 字段：只能保存最后原因，不能形成多次变更的事件历史。
- 允许直接编辑状态和有效期：实现简单，但无法判断是谁、何时、基于什么操作改变了派生记忆。
- 现在实现恢复和重建：语义与来源替换规则尚未验证，会扩大本切片范围。

## 后果

场景停止参与回答的原因可以被用户和后续研究工具检查；并发或过期页面不会覆盖新状态。代价是数据库升级到 V6，个人库必须在服务停止且完成一致性备份后显式迁移。事件目前只描述失效，不代表已经实现自动场景整理、恢复或跨层重建。
