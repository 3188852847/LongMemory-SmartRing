# L2 场景记忆：第一版需求与验收

日期：2026-09-06。当前状态：设计已接受；V5、L2 领域模型、事务存储、应用用例、受限 API 和 React 人工候选/复核页已实现，模型生成与回答使用尚未实现。

## 用户可见目标

把分散的 L1 原子记忆组织成一段可核对的生活背景，例如：

- L1：用户周五要进行毕业答辩。
- L1：用户这几天在修改答辩 PPT。
- L2 候选：用户本周正在准备周五的毕业答辩，当前主要任务是修改 PPT。

L2 不是把所有近期事实压成一段摘要，也不是稳定用户画像。与当前场景无关的“用户喜欢乌龙茶”不能仅因时间接近就被合并进上述候选。

## 第一版范围

- 从同一用户的当前 L1 中形成有标题、摘要和可空时间范围的候选。
- 查看每个候选引用的 L1，并继续查看对应 L0 原话。
- 接受、拒绝候选；保留生成器和复核记录。
- 来源 L1 退出当前集合后，把相关 L2 标为 stale（来源已变化），停止后续使用。
- 生成和保存失败时不留下缺来源或半完成的候选。

当前已提供 `/scenarios` 用户入口。用户可以显式选择至少两条 L1，人工填写标题与总结形成候选，再接受或拒绝；这只是验证数据、权限与复核链，不代表自动场景提取已经实现。日常库仍没有 L2 候选，已接受场景也没有接入聊天召回。

## 第一版不包含

- 自动从每轮聊天实时生成 L2。
- 未经确认就把模型摘要注入回答。
- 自动推断稳定性格、长期习惯或情绪原因；这些属于 L3 或更严格的推断。
- 自动修复 stale 候选、跨场景关系图、GraphRAG、主动问候。
- 把论文、网页或知识库内容作为“用户生活事实”的来源。

## 最小数据与来源约束

一个可保存的候选必须满足：

1. 标题和摘要非空，正文长度有明确上限。
2. 至少关联两条不同的 L1。
3. 这些 L1 最终覆盖至少两个不同的用户 L0 消息。
4. 来源属于同一主体，生成快照时均未退役。
5. 生成器名称和版本非空；系统记录时间带时区。
6. 若同时提供开始和结束时间，结束不得早于开始。
7. 候选、来源关联和生成审计位于同一事务。

## 合成验收场景

### A. 正常形成候选

输入两次独立用户陈述：周五答辩、最近修改 PPT。结果应形成一条 candidate，引用两条 L1 和两个 L0；尚不能进入回答上下文。

### B. 单条原话拆成多个事实

一句话同时提到周五答辩和修改 PPT，即使提取成两条 L1，也不满足“两条独立 L0”门槛；不得伪装成多来源候选。

### C. 无关事实污染

加入“用户喜欢乌龙茶”。答辩场景的来源不得仅按时间邻近自动包含该事实。

### D. 来源变化

用户纠正答辩日期，旧 L1 退役。引用旧日期的 candidate/active L2 必须可定位并转为 stale；不能继续注入回答。

### E. 接受与拒绝

接受只改变复核状态，不改写模型原摘要和来源；拒绝后不进入召回，重新生成的新候选使用新 ID，不能覆盖历史。

### F. 失败原子性

候选写入、来源关联或审计任一步失败，数据库中均不得留下孤立 L2 或部分关联。
