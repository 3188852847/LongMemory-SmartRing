# L3 用户画像：第一版验收需求

日期：2026-09-06。代码已实现人工候选、证据门槛、来源追溯、接受/拒绝、来源失效传播、受限 API 与 React 页面；个人数据库已在一致性备份和明确授权后迁移至 V8，可进行真实页面体验。

## 用户可见目标

L3 用于保存经过来源核对的稳定认识，例如：

- 用户明确偏好：用户明确表示希望助手先倾听，再询问是否需要建议。
- 系统推断习惯：多个不同日期的互动共同显示，用户通常在午后与助手聊天。

第二种不能由一次聊天、一个 L2 场景或模型印象直接得出。L3 用户画像也不等于“爱莉希雅”等助手角色设定。

## 已实现边界

- 一条记录只保存一个画像断言，类型为偏好、习惯、互动方式或行为模式。
- `user_declared` 至少追溯到一条用户 L0；页面明确标为“用户自述”。
- `system_inferred` 至少包含两个 L1/L2 来源、三条不同用户 L0，并覆盖两个 UTC 观察日；页面明确标为“系统推断”。
- 来源只能选择当前有效的 L1 或已接受的 L2，并继续展示 L0 原话与来源快照。
- 创建只得到 `candidate`；用户通过 revision 保护的二次确认接受或拒绝。
- L1 退役/删除或 L2 失效时，关联候选或生效画像自动转为 `stale`，并记录生命周期事件。
- 网页写入需要独立画像管理能力、本机会话、同源/CSRF 校验和明确确认。
- 当前候选由用户手工组织，不会打开页面就调用模型、扫描历史或自动写入。

## 当前明确不包含

- 模型辅助草稿、定时扫描、批量回填或自动创建候选。
- 将已接受 L3 注入网页或圆屏回答。
- 自动重建失效画像、撤销复核或画像版本链。
- 自动主动问候、行为原因推断、情绪诊断或画像置信分数。

## Definition of Done

1. 声明型画像没有用户 L0 时拒绝创建。
2. 推断型画像未满足“2 来源、3 用户 L0、2 观察日”时拒绝创建。
3. 候选、来源快照和生成审计在同一个事务中保存。
4. 详情能从 L3 沿 L1/L2 追溯到 L0 原话。
5. 接受/拒绝使用 revision 防止旧页面覆盖新状态。
6. 来源退役、删除或失效会使画像 stale，并留下原因；画像和证据不被静默删除。
7. 页面、HTTP API、数据库迁移及全量回归通过；真实个人库迁移和页面体验另行验收。
