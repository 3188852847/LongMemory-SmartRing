# CosyVoice 运行优化实测（2026-09-14）

本轮修改由用户明确授权。保留 Fun-CosyVoice3-0.5B、官方参考声线、既有环境、
FP16、Flow 10 步与自然标点连续播放；没有接触 Memory Core、个人库、校园接口、
外部源码或模型文件，没有安装依赖。圆屏仍需真实复测，不能将合成速度当成整轮对话延迟。

## 改动与依据

当前 Xiaozhi 已经在合成首段时接收后续文字，并在播放上一段时合成下一段。
本轮没有增加争用同一显卡的多请求推理线程。消费者先收齐标点片段再编码，
所以在服务中反复计算内部流式块无法改善圆屏首声，只增加重复计算。

服务改为完整生成标点片段，沿用长度前缀 WAV 协议；仍兼容恢复内部流式模式。
Qwen 语音 token 生成只需要最后隐藏状态，适配器跳过未使用的文本词表输出。
这不是量化、减步数或换声线。适配器只处理核对过的源码与版本，不兼容时保留原方法。

取消保护覆盖读块、解码、编码、预置和完整 WAV 回退，旧话轮在 `client_abort`
被新话轮清空后仍然失效。完整片段模式在第一次写 HTTP 前耗尽模型生成器，
确保最后一次 yield 后的请求状态清理已经执行。该保护不等于立即取消正在执行的 GPU 请求。

## 基准身份与方法

- 项目基线：`b77a569`；外部 CosyVoice：`074ca6dc9e80a2f424f1f74b48bdd7d3fea531cc`。
- RTX 4080 16GB；PyTorch `2.3.1+cu121`、Transformers `4.51.3`，原环境线程数 16/24。
- `benchmark_runtime.py` 记录项目/CosyVoice 提交、相关源码 SHA-256、模型阶段、
  WAV SHA-256、音频时长、块到达、峰值显存；输入只取既有四句合成测试文本。
- 同一进程、同种子、关闭回复缓存，交替顺序降低暖机/运行顺序偏差；两轮四句、
  两种内部模式、两种输出层模式共 32 次。包含服务 WAV 包装并在新工作线程运行。
- 内部阶段用 CUDA 事件和墙钟计时，结束后再同步；阶段存在嵌套和并发，不能直接相加。

## 可归因于代码的收益

下表为同一进程两轮均值；实时率等于生成总毫秒数除以音频总毫秒数，小于 1
表示这一组输入的生成速度超过播放速度。首个模型块不是圆屏首声：当前消费者要等整段。

| 固定句 | 原内部流式完整耗时 | 新默认完整耗时 | 原实时率 | 新实时率 |
| --- | ---: | ---: | ---: | ---: |
| 短回复 | 1781 ms | 1386 ms | 1.048 | 0.815 |
| 数字与时间 | 3785 ms | 3224 ms | 0.766 | 0.653 |
| 中英混合 | 3942 ms | 3156 ms | 0.776 | 0.621 |
| 陪伴语气 | 4229 ms | 3571 ms | 0.750 | 0.633 |

按音频时长加权的整体实时率由 **0.791 降至 0.653**，约节省 **17.5%** 总耗时。
只切完整片段已达到 0.657；跳过文本输出层额外速度收益不稳定，主要是减少显存。
峰值已分配显存由 4.876 GiB 降至 3.955 GiB，其中输出层优化贡献约 0.29 GiB。
这是该进程的 PyTorch 分配峰值，不是整张显卡总占用。

相同模式、文本和种子的 16 对输出层开关对照 WAV 哈希全部一致。
内部流式与完整片段之间的波形不要求逐采样一致，不能把前者的等值结果扩展为
后者已经通过自然度盲听。模型、参考和精度未变，声线与自然度仍需用户复听。

## 真正耗时的部分

完整片段陪伴语气例：145 次 token Transformer 共约 2695 ms，采样约 281 ms，
Flow 约 268 ms，含 F0 的 HiFT 约 115 ms；整段约 3414 ms。
内部流式同类例 Flow 合计约 1183 ms、HiFT 约 382 ms，但与 token 生成重叠。
这支持当前先避免重复 Flow/HiFT，再考虑 token 生成运行时，而不是直接安装 TensorRT。

F0 在这些请求中仅约 3～12 ms，没有证据支持搬到 CPU 或降低精度。
CPU 线程数 16→1、新工作线程、WAV 包装和是否开启计时均未解释旧进程的两倍差异。
采样占一部分时间，但本轮未改变候选选择或随机采样，避免引入声音内容风险。

## 最终真实传输验证

临时 `127.0.0.1:18771` 服务运行最终默认代码，在现有 Xiaozhi Python 环境中
用真实 WAV 解析、16kHz 重采样、60 ms Opus 编码与解码验证四句两轮，无设备发送。

- 八次实时率 0.579～0.807；短句首个 Opus 可用 1348～1438 ms。
- 重采样通常不足 2 ms，首次导入约 13 ms；整段 Opus 编码约 15～48 ms。
- 所有包可解码，包数等于补齐最后一帧后的期望数量；补零不足一帧。
- 新默认 health 为 `hidden_only=true, model_streaming=false`；两个回退参数真实
  启动后变为 `false/true`，短句返回两个模型 WAV 块且可正确编码。
- 测试临时进程均结束。原日用 18770 进程仍保持运行，没有偷换成不受面板管理的服务。
- `tests/unit/development` 最终 356 项通过。中途一次既有 Tk 窗口测试发生中文
  Tcl 路径解析错误，单独复跑与随后完整复跑通过；没有为此修改无关启动面板代码。

## 尚未解释的旧进程差异

旧日用进程同样四句约 3.77/7.59/8.76/10.59 秒，实时率约 2.05/1.61/1.80/1.65；
使用旧代码模式的新服务约 1.73/3.13/3.56/4.24 秒，实时率约 0.96/0.75/0.72/0.70。
请求随机结果与时长不同，已使用实时率比较，仍不能确定原因。

已排查启动脚本/模型路径、CPU 优先级与亲和性、七项 GPU/线程环境白名单、
进程 PowerThrottling，以及 GPU 专用/共享显存快照，未得到确诊证据。
旧进程只使用约 82 MiB 共享显存，该快照不支持大规模权重换页。
**不能把重启/进程状态带来的额外收益归因于本轮代码，也不能保证长时间运行不退化。**

## 日用生效、回退与下一次验收

在启动面板停止服务后重新启动即可加载新代码。现有控制入口只支持整套启停，
本轮没有为了更新 TTS 而重新启动读取个人库的整套日用系统。

隔离复现（项目根目录，既有 CosyVoice 环境，不联网下载）：

```powershell
& 'D:\ESP32-Workspace\CosyVoice\.venv\Scripts\python.exe' -B scripts/development/cosyvoice/benchmark_runtime.py --variants baseline hidden_only --cases short_reply numbers_time mixed_language expressive --compare-modes --repeat 2 --service-path --worker-thread
```

服务回退参数为 `--model-streaming --no-hidden-only`，分别恢复内部流式和原文本输出层；
可先在空闲 18771 端口验证，不占用日用端口。没有模型/依赖迁移需要恢复。

下一次最小真实验收：同一负载下连续五轮普通短回答，含一次生成期间打断和一次播放期间
打断，随后继续一轮；取得 V6 数据后比较下列指标。不要求用户向记忆库写入虚构事实。

| 指标 | 本轮状态 / 后续门槛 |
| --- | --- |
| 停嘴到首包、LLM 首字 | 未调用回答模型，未测；仍需单独计入现有约 700 ms 判停与 ASR |
| TTS 首段、每段与整体实时率 | 固定测试首段约 1.4 秒、每段均小于 1；真实目标每段与整体 <1 |
| 最大连续欠载 | 未测扬声器；服务端先依据实际各段开始/完成与包时长估计，再核对听感 |
| 声线一致性、自然度 | 输出层优化 16 对波形一致；完整模式的人工听感待验收，不接受可闻退化 |
| 打断响应 | 自动验证过期包丢弃；实机停止与接续待测，GPU/阻塞读取尚非即时取消 |

RTF<1 不保证每段之间无空档：首段很短、下一段很长时，仍可能在标点处等待。
新数据若还出现秒级空档，再评估后续片段长度与音频库存；不恢复词中直接播放模型块。
若合成已达标但停嘴到首声仍慢，应处理回答模型首输出等待；本轮没有越过校园接口限制。
