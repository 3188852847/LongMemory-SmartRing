## 一、提前听写：已通过合成基准

先用本机 CosyVoice 生成三条公开固定语音，只在内存中处理：

- 请帮我想一个整理书桌的简单办法。
- 我想先喝一杯水，然后再开始工作。
- 为什么傍晚的天空会变红？

真实语音长度约 2.40–3.64 秒。保持相同音频，分别补 300/700ms 静音尾，四轮交替
共 24 次真实 SenseVoice 推理；12 对结果完全一致，推理耗时 198–265ms。它只证明
这三条清晰合成输入的一致性，不等于真实噪声、轻声尾音或自然停顿的准确率。

另从已审查的上游源码提取实际 `receive_audio`、`handle_voice_stop` 和
`speech_to_text` 方法，复用真实模型，按 60ms 节拍输入静音，正式端点设在第 12 帧
约 720ms。提交端和上报端替换为无副作用内存接收器，不调用真实聊天或记忆。
原路径和预取路径交替，两轮、三句，共 12 次完整输入流程：

| 指标 | 原路径 | 提前听写 |
|---|---:|---:|
| 停嘴到文字就绪中位数 | 980.2ms | 731.5ms |
| 最快–最慢 | 961.8–1031.9ms | 725.1–734.4ms |
| 正式端点前提交 | 0 | 0 |
| 成对转写一致 | 六对一致 | 六对一致 |

中位数改善约 **249ms**。实际预识别仍需 224–245ms，提前计算与停嘴等待重叠，
所以正式端点后的剩余识别等待四舍五入为 0ms；不是模型变成零耗时。
这是音频输入到转写的隔离实验，不包含 LLM、记忆、TTS、真实麦克风及扬声器。

预取最多一次、输入快照限 1–8 秒；继续说话即废弃。失败、空结果、快照变化和
不支持的模式使用完整识别。底层线程不能强制取消，失效任务未结束可能使正式识别
排队；须通过真实停顿续说测试观察，不能只展示命中收益。
若 VAD 把轻声尾音判成静音，提前快照可能漏掉仍可被完整 ASR 识别的尾字；
真实验收必须包含低音量句尾和停顿续说，出现差异就切回原策略。

Windows QoS 同进程交替对照中，CPU 听写默认中位 231.6ms，HighQoS 241.9ms，
没有稳定收益。因此未给 Xiaozhi 增加该调度设置，也未更换 ASR 的 CPU 依赖。

原始数值只在本机 Git 忽略目录 `.test-runtime/`：
`asr-prefetch-seed-results.json`、`asr-prefetch-integration-results.json`。

相同通用系统提示、256 token 上限、非思考、默认温度，交替原提示与语音短句规则。
没有注入日用个人角色或历史，因此不是完整日用模型请求的替身。

第一批八次请求：原提示首字 1194–5790ms，实时提示 2125–5717ms；响应字符数
原提示 50–122，实时提示 33–39。短句策略控制了回答长度，首字波动太大，不能
宣称它已降低云端首字；首段字符数也只是启发式，用户要求详细时仍保留必要内容。

## 三、跨轮连接复用

实际 SDK 的 HTTPX 默认空闲连接期限为 5 秒。独立基准保持 SDK 流读取/关闭语义，
每组先请求一次、空闲 7 秒、再请求；对照 5 秒与 120 秒，第二轮反转组序。只记录
`connect_tcp`/`start_tls` 事件计数和时间，不读取 trace 信息字典或输出请求内容。

HTTP/1.1 的两轮八次请求全部重新建立 TCP/TLS，**仅延长到 120 秒没有成功复用**。
SDK 收到 SSE 结束标志后的关闭行为也属于验证条件，不能用独立裸 HTTP 客户端
的复用结果代替日用 SDK。

随后仅启用本机已经安装的 HTTP/2 支持，一轮四次请求均实际协商为 HTTP/2：

| 空闲期限 | 请求 | TCP/TLS 新建次数 | LLM 首字 |
|---|---|---:|---:|
| 5 秒 | 首次 | 1 / 1 | 2600ms |
| 5 秒 | 空闲 7 秒后 | 1 / 1 | 2551ms |
| 120 秒 | 首次 | 1 / 1 | 1325ms |
| 120 秒 | 空闲 7 秒后 | **0 / 0** | **766ms** |

120 秒组第二次请求成功复用，直接证据是 TCP/TLS 新建事件为零，不只是响应更快。
同组首次到下一次首字缩短约 559ms，但样本很小、云端仍有波动；不把两组之间
约 1.8 秒差值全部归功于此改动，也不把 766ms 称为停嘴到首声。

因此实时优先启用 **HTTP/2 + 120 秒空闲连接**，仅限官方 DeepSeek 语音 provider，
使用公开 SDK/HTTPX 构造入口，保留认证、超时和代理默认。HTTP/2 依赖已安装
（h2 4.4.1、hpack 4.2.0、hyperframe 6.1.0），没有新增安装。其他机器缺少可选
依赖时回到原客户端；配置和证书等错误仍正常报告。原策略不安装此适配。

首次请求、空闲超过期限、服务器断连或设备重连后新建 provider 仍可能建连。
没有付费后台保温请求，也不承诺每次云端首字固定达到本次最小值。

```powershell
& 'D:\ESP32-Workspace\xiaozhi-esp32-server\main\xiaozhi-server\.venv\Scripts\python.exe' -B scripts/development/xiaozhi/benchmark_voice_keepalive.py --run-official --env-file .env.deepseek.local --repeat 2
# HTTP/2 单轮四次请求对照
& 'D:\ESP32-Workspace\xiaozhi-esp32-server\main\xiaozhi-server\.venv\Scripts\python.exe' -B scripts/development/xiaozhi/benchmark_voice_keepalive.py --run-official --env-file .env.deepseek.local --http2
```

## 验收和后续

真实圆屏验收仍需用户说话。相同拾音距离、音量和模型下，比较实时优先与原策略
各十轮，分别包含短问、较长问、停顿后继续说、播放中插话。先预热一轮，冷态另记。

| 指标 | 本轮判定标准 |
|---|---|
| 停嘴到首包 | 同样问题比较中位数和最慢值，目标中位至少减少 200ms；不可混用模型首块 |
| LLM 首字 | 与网络重建次数一起看；报告分布，不用挑选的最快样本 |
| TTS 首段/每段 RTF | 声线、精度不变；不要因过短首句重新出现第一段后的长空档 |
| 最大连续欠载/整体 RTF | 记录服务端库存估算与听感，目标不增加 >300ms 空档；估算不冒充扬声器测量 |
| 识别准确性与提交 | 续说不丢尾字、不过早回答、不重复归档；失败回到完整识别 |
| 声线与自然度 | 同一 CosyVoice 参考音色；短句风格由用户听验，详细问题保留必要信息 |
| 打断响应 | 旧音频继续使用既有过滤；预识别失效后不得提交旧结果 |
| 显存/资源 | 不新增 GPU 模型；ASR 仍 CPU，观察正式任务排队和误触发次数 |

不以本轮完成代替整套实时对话达标。若官方首字波动继续主导，下一步应比较独立
回答服务或已准备的豆包备用模式，而不是继续压缩自然语音帧或侵入记忆核心。
