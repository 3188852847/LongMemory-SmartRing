# Windows 调度修复后的模型内部流式复验

## 目的与边界

在 `bfc5b08` 的 HighQoS 修复之后，重新检查内部流式是否仍会供给不足。
本轮只新增实验工具和数值回归，不修改日用 TTS、Xiaozhi 适配器、设备或 Memory Core。
使用现有模型和依赖，参考声线、FP16、10 步 Flow、hidden-only 保持不变；不访问
校园接口、回答供应商、个人记忆或真实对话。实验进程在完成后退出，不留下模型常驻。

“首块”是本地合成器经 WAV 封装后可用的时间；“首播”是按块到达与 60ms 帧推导的
预计起点，均不等于停嘴到圆屏扬声器出声。整个文本已知，没有模拟 LLM 增量到达。

## 验证分四关

1. **相同模型的首块与总速度。** 四条公开固定句，在同一个进程交替测试完整生成与
   内部流式，每组重复三次。缓存关闭、固定种子，记录每块时刻、时长、样本数、完整
   耗时及 PyTorch 显存峰值。种子不保证并行路径的音频逐采样一致。
2. **相同日用切段的连续性。** 复用当前首段/标点合并规则，串行合成相同片段序列，
   避免将整条长回答作为日用完整模式的首段，夸大流式收益。按同一时钟记录各段起点，
   比较立即首播，以及额外等待 120/240/360ms 的因果策略。
3. **真实音频发送与取消。** 候选方案需经过实际 WAV→PCM→Opus 和受限发送测试；
   一段未结束时插话，不得续发旧轮，也不得拖住下一轮。模型取消和音频丢弃分别测量。
4. **圆屏盲听与整轮验收。** 同一声线、相同句子比较 A/B；检查开口、词中突停、句间
   等待、自然度和打断后接续。同时记录停嘴到首包、LLM 首字与 TTS 首块，不能混用。

本轮完成前两关的测量和局限分析，**第三、四关尚未完成，不切换日用播放方式**。
后续接入门槛建议：较长小句首声中位数至少改善 200ms，短句不额外回退超过 100ms；
最大连续欠载不超过 100ms、不得再出现超过 300ms 的空档；总体 RTF 应有低于 0.8
的余量。自然度、声线和打断须听验，不以数值估算代替。以上是候选目标，非通过结论。

## 首轮：完整文本，不等于当前日用首段

四句各三轮，首块时间取中位数；两种方式都复用服务 WAV 封装与真实请求线程，未走 HTTP。

| 公开句型 | 完整生成首块 ms | 内部流式首块 ms | 流式最大预计欠载 ms | 完整/流式 RTF 中位数 |
| --- | ---: | ---: | ---: | ---: |
| 短回复 | 1321 | 1280 | 0 | 0.768 / 0.981 |
| 数字时间整句 | 2793 | 1508 | 0 | 0.591 / 0.706 |
| 陪伴语气整句 | 3181 | 1586 | 23.8 | 0.564 / 0.707 |
| 中英混合整句 | 2819 | 1474 | 0 | 0.573 / 0.721 |

第一块都含 1360ms 音频，末尾不足 60ms 的部分留给下一块，所以初始可释放 1320ms。
180/360/600/900ms 水位均被第一块一次满足，没有改变首播时间。额外等 120ms 可将
这批预计欠载降为 0，但这是增加时钟等待，不是水位策略突然具备了预测能力。
本机没有复现 150ms 首块，不能把“支持流式”解释成当前环境已达到宣传值。

本批 PyTorch 最大 allocated 显存完整约 3.955GiB、流式约 4.622GiB；reserved 约
4.9GiB 且受同进程分配器历史影响。这不是整机显存峰值或每个生产进程实际占用。

## 最终：保留相同日用切段

三类多片段文本各两轮，每条均按当前策略形成两个 TTS 片段；同一进程交替执行。
全局偏移在每次模型计时真正开始时取得，不把线程创建和种子准备误减到音频时刻。
每个 TTS 片段单独计算 60ms 尾帧补齐，再将释放的帧平移到统一时间轴。为避免把 EOS
提前，保守把每段最后一块记在 `completed_ms`；这可能比实际完整帧晚约 10～20ms。
段间包含实验文件归档开销，不能据此声称获得了真实设备时间线。

| 句型 | 当前完整片段首播中位 ms | 内流首播中位 ms | 提前量 ms | 完整/内流最大欠载 ms |
| --- | ---: | ---: | ---: | ---: |
| 数字时间 | 1695 | 1548 | 147 | 0 / 0 |
| 陪伴语气 | 2180 | 1560 | 620 | 0 / 0 |
| 中英混合 | 1321 | 1336 | -15 | 796 / 258 |

额外等待 240ms 后，这批内部流式最大欠载为 18.4ms；等待 360ms 则为 0。
相应首声也分别晚 240/360ms，数字句和短句的有限提前量会被抵消。
不能把这点估算余量当成真实网络、编码和设备抖动已有保证。

按实际音频时长计算、排除归档的序列 RTF：数字句完整约 0.629～0.693、内流
0.762～0.832；陪伴句完整约 0.644～0.657、内流 0.731～0.778；中英混合完整约
0.660～0.716、内流 0.812～0.895。流式更早交付的同时，整段计算成本增加。

## 结论与下一步

- Windows 修复后，之前的“所有流式块都追不上播放”不再成立；较长小句有继续验证价值。
- **不能全部打开流式后就接入日用。** 短句收益小，固定额外等待会反向增加首声；
  中英混合跨片段仍有供给空档，单看内部块不够。
- 下一候选应比较“短句完整生成、较长片段内部流式”的选择策略，并保留原完整模式。
  片段长短不能只凭字数当作已知音频时长；阈值和取消需要新的独立验证，当前未实现。
- 240ms 固定等待在本批可减小空档，但没有消除生成成本；水位和缓冲只能换取余量。
  无需为这组结果先安装 TensorRT 或更换 TTS，也没有证明可以省掉约 2.4 秒的回答等待。

`--punctuation-segments` 复用当前切段，记录每段起点及统一序列，不修改日用服务。

音频触发水位和固定延迟；不读取未来缺口决定首播，也不自动把延迟调到“结果为零”。
