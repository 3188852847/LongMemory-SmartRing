# 日用 CosyVoice 额外变慢：Windows QoS 可逆对照

## 范围与方法

代码基线 `c0e4d17`，既有 RTX 4080 / PyTorch 2.3.1+cu121 / Transformers 4.51.3 /
Fun-CosyVoice3-0.5B；FP16、完整片段、hidden-only、官方参考音色保持一致。
保留原日用 18770 进程和其他服务，同时启动独立 18771。未读取个人库、对话正文、
原始录音、密钥或完整日志；只读 V6、health、性能环境白名单和进程身份。

固定公开短句“好呀，我们慢慢来。”与数字句“现在是下午三点半，明天上午九点我们
再继续。”。串行 POST `/v1/audio/speech`、`cache:false`，不经过设备、回答模型或
记忆，音频仅用于内存解析实际时长。不固定随机种子，因此音频不逐采样相同。

RTF（生成实时率）= HTTP 完整响应耗时 / WAV 实际音频时长，小于 1 表示合成快于播放。
四阶段为请求前后 health 差值；每次必须只有一次 LLM/Flow/HiFT 调用，文本整理两次。
这些是方法墙钟时间，不能当作纯 GPU 时间或任意相加。

## 新旧进程对照

同一句短句按旧—新—新—旧执行，关闭缓存：

| 进程 | 生成耗时 ms | 音频时长 ms | RTF |
| --- | ---: | ---: | ---: |
| 日用 | 3706 | 2000 | 1.853 |
| 独立 | 1249 | 1800 | 0.694 |
| 独立 | 1331 | 1920 | 0.693 |
| 日用 | 2893 | 1920 | 1.507 |

相同模型共驻条件下仍有差异，不能将旧/新比较当作代码提速或单纯显存不足证据。
BGE 明确在 CPU；FunASR 默认设备为 CUDA，但其共驻不是这组进程差异的充分解释。

## 同一个慢进程，仅切换调度

## 实现、验收与局限

实现限于独立 CosyVoice 服务入口与 `windows_qos.py`。启动时明确 HighQoS、读回
验证、失败保持原路径，`--system-qos` 可回退；不设置全局电源、CPU 优先级或锁频。
API 语义依据[微软 SetProcessInformation 文档](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation)
及[QoS 层级文档](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service)。

这组样本支持保留当前 TTS，优先修复其日用运行速度。尚未证明任意长答无欠载，
也没有测出新策略的停嘴到首包、真实打断时间、声线主观评分或日用单实例显存峰值。
模型与参考音色未变只能说明设计上未改声线，不能代替自然度听验。
下一次圆屏普通对话验收目标：逐段 RTF 通常小于 0.8，服务端预计最大连续欠载
不超过 300ms，听感无突停；首字约 2.4 秒的问题需要独立优化。

最终软件验证：开发目录 439 项通过，包含 18 项纯替身 Win32 测试和服务入口的
设置顺序、禁用、失败继续启动测试。新代码在独立 18771 实际启动后，health 回读
`windows_qos.applied=true`、控制位 `1/0`；固定数字句生成 2941ms、音频 5120ms，
RTF 0.574。独立代码复核未发现必须修复的缺陷。

验证结束后，已再次核对当前日用进程身份，为其显式应用 HighQoS 并读回 `1/0`，
保留至该进程退出；未重启 Xiaozhi 或记忆服务。当前进程固定短句 1451/2040ms、
数字句 2649/5040ms，RTF 分别 0.711/0.526。它在更新前已启动，health 不会自动
新增源码中的 QoS 字段；后续从原面板启动的新声音进程才会包含完整启动快照。
临时 18771 服务已结束，不保留第二份模型常驻。
