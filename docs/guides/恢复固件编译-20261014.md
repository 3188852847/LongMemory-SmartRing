## 第一步：所有者下载 SDK、工具与源码

在新打开的 PowerShell 中运行，不在已激活的 ESP-IDF 子终端点源本项目脚本：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "D:\03-项目\01-正式项目\智慧圆屏\scripts\development\run_firmware_restore.ps1" -ProxyScript "D:\10-开发配置\网络与代理\开发代理.ps1"
```

入口使用已验收的 EIM 0.19.0，核对其 SHA-256；固定克隆 SDK，核对 HEAD、子模块与官方工具版本；通过 uv 取得 SDK 自用的 Python 3.11.15，使用 EIM fix 准备这个新 checkout 的工具和专属环境，再稀疏取得固定厂家源码。不重新 install 非空 SDK，不自动装公共前置工具，不部署旧 SDK、组件、模型或镜像。

新 SDK 的 TOML/log 分别为 ESP 根的 `config/smart-ring-idf-5.5.4.toml` 与 `logs/smart-ring-idf-5.5.4.log`。EIM 0.19.0 fix 的默认 C 盘版本登记行为已在本机复现；入口只将厂商实际 finished 记录合并到 D 盘清单，并保留该清单原默认选择。写入前保留原 D 盘登记副本，不调用旧的 6.1 修复脚本。实际生成的 TOML 中 `idf_versions` 仍写默认 `v6.1`，而 `path`、`version_name`、安装后的 SDK commit、专属 profile 与工具均为 5.5.4；该 TOML 是厂商执行记录，不能直接当作完整恢复锁。恢复时使用本项目固定 SDK 的入口命令和版本核对，不直接据此重新 install。

代理只在本进程加载与恢复；SDK/Python/PATH 变量只在独立进程改变。失败停止，不自动重试、不删除中断目录或部分资源。单独续接可在相同命令后加 `-Stage Sdk` 或 `-Stage Sources`；先把报错最后一段交给助手核对，不盲目反复安装。

## 第二步：核对环境并取得全新组件

第一步完成后，由助手先运行 `invoke_firmware_build.ps1 -Action Check`，核对 SDK commit、Python、idf.py、CMake、Ninja、Xtensa 命令实体与版本、pip check。SDK 安装完成不代表编译成功。

确认后，所有者执行以下联网配置阶段，组件管理器按项目版本记录取得组件及随包字体、唤醒模型等资源：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "D:\03-项目\01-正式项目\智慧圆屏\scripts\development\invoke_firmware_build.ps1" -Action Configure -ProxyScript "D:\10-开发配置\网络与代理\开发代理.ps1"
```

该阶段从新厂家 checkout 创建 `src`，在七个基线文件摘要一致后应用累计补丁，核对部署后摘要与反向应用。现有 `src` 不覆盖；失败的临时副本保留。默认板型配置由小型 `sdkconfig.restore.defaults` 重建，不复制旧 sdkconfig、旧路径或网络凭证。

`restore-0012.patch` 包含本项目从早期界面调整到 0012 持久会话的实际源码修改；早期补丁缺失时，依据历史参考源码与已核对的官方基线整理出累计差异。规范化为 LF 并使用零上下文补丁，应用前须核对全部基线摘要，应用后核对全部结果摘要与反向检查；Git 属性固定新补丁为 LF，避免 Windows checkout 改写摘要。保留原 0007–0012 补丁与实验记录。没有部署厂家旧源码、生成的 lang_config.h、个人壁纸或编译镜像。

`components.json` 只保存历史解析出的 64 个组件/SDK 版本与摘要、依赖关系，用于重建锁文件并重新下载。它不是旧 managed_components；组件源码、字体和模型仍由组件管理器全新获取。SDK 的 Python 包由官方约束解析，后续记录实际版本，不把旧包快照或 TOML 宣称为完整离线锁。
