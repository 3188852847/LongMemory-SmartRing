# 代码健康检查与渐进重构

## 目的

本检查点服务于后续产品开发，不以“文件越小越好”为目标。只有已经出现职责混合、
跨域耦合、重复契约或测试困难的代码才进入重构；数据库、HTTP 语义和设备协议默认
保持兼容。

以下数字用于定位热点，不单独构成拆分理由：

| `entrypoints/api/server.py` | 500+ | 应用装配与部分设备路由仍混合 | 中 |
| `web/react-chat/src/api.ts` | 380+ | 多业务域类型和请求方法共用一个文件 | 中 |

真实触发信号是：声音设置曾错误依赖当前必须选择 LongMemory，导致切换到小智本地
记忆后 TTS 测试台不可用。这说明配置域边界需要自动化测试，而不只是文档约定。

测试基础设施也属于代码健康范围。pytest 不再让所有进程共用固定的
`.pytest-tmp`：每次运行使用项目内独立目录，避免 Windows 用户临时目录 ACL
问题，也避免并行测试或异常中断进程争用同一个 SQLite 文件。

## 重构原则

1. 先写或确认特征测试，再移动代码；特征测试锁定当前可观察行为。
2. 每个提交只拆一个职责，不和新产品能力、数据库迁移或协议升级混在一起。
3. 优先组合与显式依赖，不用巨型 Mixin 或 `__getattr__` 隐藏依赖。
4. 文件行数是线索，不是指标；稳定 SQL 定义和完整协议表允许保持集中。
5. 重构后必须运行相关测试和完整回归；无法实测的设备行为不得标记为已验证。
6. 不为“以后可能用到”创建空层、空接口或新框架。

- 行为与公开错误码不变，或另有 ADR 明确记录变化。
- 不读取、迁移或重写个人数据库。
- 相关测试通过，完整套件无新增失败。
- 没有新增循环依赖、重复常量或隐式全局状态。
- README、路线图或架构说明只记录真实完成项。
