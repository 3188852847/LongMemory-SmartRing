# 技术策略与技术雷达

更新：2026-09-06。本文记录技术选择的当前状态和触发条件，不把候选技术写成已实现功能。正式决定见 [ADR-0033](../adr/0033-staged-technology-adoption.md)。

## 1. 评审规则

每项新技术都必须回答：它解决哪个已经观察到的问题；不用它的当前代价；引入、迁移、学习和长期维护成本；是否侵入记忆核心或数据格式；如何测试、回退和移除。结论只能是“现在采用、隔离试验、条件触发或当前拒绝”之一。

预测未来会使用不能单独构成采用理由。若采用成本会随规模快速上升，且当前需求已经出现，应尽早建立基础；若技术只是替换已工作的实现，则先用中立契约降低锁定，再等待真实触发。

## 2. 当前基础

| 技术 | 当前职责 | 状态 |
|---|---|---|
| Python 3.12、uv、pytest | 应用、环境和测试 | 保留 |
| SQLite | L0/L1、会话与本机设置持久化 | 保留 |
| aiohttp | LongMemory 本机 API、小智相关 HTTP | 保留；LongMemory 入口继续变薄 |
| React、TypeScript、Vite、Ant Design | 本机控制台 | 保留并渐进统一页面 |
| 本地 BGE、PyTorch、Transformers | 可选日常混合召回和隔离实验 | 保留，按显式配置启用 |
| VoxCPM2 适配层 | 可替换本地 TTS | 保留，听感和延迟继续实测 |

## 3. 现在采用

| 技术 | 解决的问题 | 边界 |
|---|---|---|
| React Router | 多页面路由、共享导航、兼容入口和错误页 | 不引入 SSR，不要求常驻 Node 服务 |
| TanStack Query | API 查询、缓存、刷新、轮询和 mutation 状态重复 | 危险写操作不自动重试；CSRF 与结果核对不变 |
| Vitest + React Testing Library | React 组件交互缺少自动验证 | 不替代 Python API/领域测试 |
| Pydantic | API 和模型结构化输入大量手写校验 | 先做入口试点，不进入 Memory Core；保持既有错误契约 |

依赖安装、锁文件更新和浏览器下载按项目约定由用户执行；代码变更必须在锁定版本下验证。

## 4. 条件触发

| 技术 | 触发条件 | 采用前必须验证 |
|---|---|---|
| Playwright | React 日常页面基本统一 | 少量关键路径、失败 trace、本机数据隔离 |
| SQLite FTS5 | 现有词面召回质量或延迟出现可测缺口 | 中文 tokenizer、冻结对照、索引一致性 |
| 持久化向量缓存 | 启动重建或增量编码成为瓶颈 | 模型指纹、失效、重建、备份恢复 |
| APScheduler | 圆屏待机主动投递验证通过 | 幂等、勿扰、频率、过期、取消、重启恢复 |
| SSE/WebSocket | 轮询造成可测问题 | 断线、重连、状态版本和资源释放 |
| Hypothesis | 记忆状态组合超出手写用例覆盖能力 | 领域不变量和失败最小化结果可解释 |
| pydantic-settings | 多处配置已有明确权威来源 | 密钥边界、优先级和旧配置迁移 |
| OpenTelemetry | 现有事件记录不能定位跨进程故障 | 脱敏、存储成本和本地关闭能力 |
| FastAPI | 外部 API、OpenAPI/客户端生成、多用户或 HTTP 维护瓶颈 | 完整迁移清单和等价安全/错误测试 |
| PWA/Tauri | 日常启动、安装或通知体验仍不足 | 后台边界、更新、签名和回退；Electron 非默认 |
| ONNX Runtime/TensorRT | 本地模型存在测得的性能瓶颈 | 输出一致性、显存、冷启动和维护收益 |

## 5. 当前不采用

| 技术族 | 原因与重新评估边界 |
|---|---|
| LangChain、LangGraph、Deep Agents | 当前没有需要其承担的复杂自主工作流；若未来出现可持久、分支、人工介入流程，再与自有轻量编排对比 |
| Redis、Celery、RQ、微服务、Kubernetes | 单机单用户没有分布式协调收益，反而增加启动和故障点 |
| Qdrant、Milvus、Weaviate 等独立向量库 | 当前规模可由 SQLite 与本地索引承担；数据量和查询需求先测量 |
| Neo4j、GraphRAG | 尚无图查询必要性；知识平面继续通过中立 `KnowledgeProvider` 设计 |
| SQLAlchemy、Alembic | 当前直接 SQL 与版本迁移明确；若实体/查询和迁移数量显著增长再评估，二者不因流行自动成套引入 |
| Docker | Windows GPU、音频、局域网设备和多 Python 环境下成本高；需要可移植部署时再做实验 |
| Semantica、TencentDB 等外部记忆实现直接作为核心 | 用作设计和实验参考，通过方法/知识接口适配，不让个人记忆数据模型被外部项目锁定 |

## 6. 近期实施顺序

1. 已建立 React Router、TanStack Query 的安全默认值和统一 AppShell。
2. 已加入 Vitest/React Testing Library，验证共享导航、API 安全约束与危险 mutation 默认不重试；页面级错误状态随迁移继续补充。
3. 已以设备与状态页验证查询、5 秒轮询和受控 mutation，保留旧页回退。
4. 下一步聚合角色/声音设置；实验中心随后迁移，逐项清理旧资源。
5. 选择一个小型 Python API 做 Pydantic 契约试点；验证后渐进覆盖。
6. React 页面基本统一后加入 Playwright 关键流程。
7. 收束基础设施并回到 P3：事实变化、L2 场景、L3 用户画像和日常召回质量。
8. P4 先验证主动投递，再选择持久调度技术。

任何候选提前进入主线，都需要说明新证据、范围、迁移与回退，并通过新 ADR 更新本表。
